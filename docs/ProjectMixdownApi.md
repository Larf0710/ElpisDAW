# Project Mixdown API

Status: backend foundation and pure Project registration contract implemented;
runtime coordination and UI are not implemented.

## Endpoint

```text
POST /api/v1/project-mixdowns
```

The endpoint requires the per-launch Local Engine token and
`Content-Type: application/json`.

The exact request envelope is:

```json
{
  "operationId": "mixdown-operation-00000000-0000-4000-8000-000000000000",
  "plan": {},
  "protocolVersion": "1"
}
```

`operationId` is generated by the client for one intended Mixdown operation.
It is not the Worker `requestId`, and it is not derived from the Plan hash. The
`plan` value must be one exact immutable `ProjectMixdownPlan`.

## Same-Process Idempotency

The Local Engine retains an in-memory operation receipt for the lifetime of the
current process.

- The same `operationId` and the same canonical Plan share one execution and
  return the same terminal outcome.
- Object property order does not change Plan identity. Array order and all Plan
  values remain significant.
- The same `operationId` with a different canonical Plan returns
  `PROJECT_MIXDOWN_OPERATION_CONFLICT` with HTTP 409.
- A new `operationId` while a Mixdown is active returns
  `PROJECT_MIXDOWN_BUSY` with HTTP 409.
- Same-operation recovery is resolved before the generic busy check.

The receipt is not persisted. A Local Engine restart ends this recovery scope.
This API does not claim exactly-once recovery across Engine restart. Durable
operation receipts require a separately reviewed storage contract.

## Disconnect and Cancellation

The server installs request-abort and premature-response-close listeners before
reading the request body. One operation AbortSignal flows through
`ProjectMixdownService` to `ProjectMixdownWorkerClient`.

Client disconnect cancellation is best-effort. A disconnect is not proof that
the Mixdown did not finish. The operation remains active until Worker
termination, service settlement, and staging cleanup have completed.

Atomic finalization is the irreversible commit boundary. A finalized WAV is
not deleted merely because its HTTP success response could not be delivered.
Recovery reuses the original request and `operationId` to retrieve the retained
outcome without creating another WAV.

## Client Outcome Classification

`LocalEngineClient` uses a dedicated 32-minute Mixdown request timeout. The
Worker timeout remains 30 minutes; the additional time is reserved for service
settlement and cleanup.

- An abort observed before dispatch is `not-dispatched` / `canceled`.
- A valid success response is confirmed.
- A structured HTTP rejection is confirmed.
- Post-dispatch user cancellation, timeout, offline failure, or invalid response
  is `unknown-outcome` with a distinct cause.
- `unknown-outcome` never triggers an automatic retry.
- `recoverProjectMixdown` requires the original unknown outcome and rejects a
  mismatched `operationId` before dispatch.

## Shutdown

Local Engine shutdown stops accepting new mutations, aborts and awaits the
active Project Mixdown, waits for Worker termination and service cleanup, then
discards any remaining staging reservations and closes connections.

## Response Boundary

Successful responses contain the public `operationId`, protocol version, safe
Artifact metadata, bounded renderer provenance, and Mixdown metadata. They do
not contain the immutable Plan, external source paths, staging paths, final
absolute paths, or Worker request identity.

## Project Registration Contract

`createProjectMixdownArtifactCandidate` derives one typed Raw Mixdown Artifact
candidate from the original versioned Request, the confirmed or recovered
Operation, the current Project, and one existing Master Audio Clip target. The
candidate is suitable for the generated-audio availability check and does not
mutate the Project.

`createProjectMixdownRegistration` requires Local Engine availability evidence
for a new Artifact before it returns a registered Project update. It then:

- stores a dedicated `ProjectMixdownAudioArtifact` and
  `ProjectMixdownAudioClipTake`;
- uses the public `operationId` as `sourceOperationId`, never as a Job ID;
- retains the exact canonical Plan JSON and typed input Clip, source, Track,
  Artifact, and ClipTake lineage;
- detects same-operation recovery before current-source drift validation;
- rejects a reused operation with a different Plan or outcome;
- rejects a Master target that was also rendered as an input;
- updates only the target Master Clip and never mutes or deletes source Tracks;
- preserves a current Master Take when the new Raw Mixdown is registered
  inactive.

The canonical Plan is retained in Project persistence as operation provenance;
it is not added to the Project Mixdown HTTP response. Project registration does
not make the Local Engine receipt durable and does not extend API outcome
recovery across an Engine restart.

This slice does not create a Master Track or Clip, dispatch Mixdown from the
App, add visible UI, implement Connected Inputs, run Master processing, or
export the final WAV.
